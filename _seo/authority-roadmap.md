# مسیر راه: مرجع فارسی گزارش صعود

هدف محصول: `https://www.kavehrs.com` منبعی باشد که کوهنورد فارسی‌زبان **قبل از برنامه** برای مسیر، هوا، تجهیزات و تجربهٔ اجرا به آن برگردد — نه فقط آرشیو باشگاهی بعد از صعود.

این فایل منتشر نمی‌شود (`_seo/` در `_config.yml` exclude است).

منابع کیفیت (نه بلاگ‌های SEO):

- [Google: Creating helpful, reliable, people-first content](https://developers.google.com/search/docs/fundamentals/creating-helpful-content)
- [Google: SEO Starter Guide](https://developers.google.com/search/docs/fundamentals/seo-starter-guide)
- [schema.org Article / Mountain / CollectionPage](https://schema.org/)
- قوانین داخلی: `.cursor/rules/logbook-reports.mdc` و `AGENTS.md`

---

## تعریف «مرجع» برای این سایت

مرجع بودن اینجا یعنی:

1. برای پرسش‌هایی مثل «گزارش صعود قله X»، «مسیر کلوان کهار»، «یخ‌نوردی خور»، صفحهٔ این سایت **کامل‌تر و قابل‌اعتمادتر** از خلاصهٔ باشگاهی باشد.
2. خواننده بعد از خواندن گزارش، برای تصمیم go/no-go یا بسته‌بندی **دوباره جستجو نکند**.
3. گوگل و خواننده ببینند محتوا **تجربهٔ دست‌اول** است (عکس واقعی، زمان‌بندی اجرا، هوا از منبع دقیق قله).
4. پوشش رشته‌ها در `_data/logbook_disciplines.yml` به‌تدریج پر شود — فقط با برنامه‌های واقعی، نه با مقالهٔ ساختگی.

مرجع بودن **برابر با بیشترین تعداد گزارش** نیست. باشگاه‌هایی مثل اسپیلت ده‌ها گزارش کوتاه تکراری دارند. مزیت این سایت عمق عملیاتی + یکتایی روایت است.

## وضعیت فعلی (اوت ۲۰۲۶ / مرداد ۱۴۰۵)

| مورد | وضعیت |
|---|---|
| گزارش‌های منتشرشده | ۲۲ در `/logbook/` |
| SEO فنی پایه | canonical، sitemap (~۳۵ URL)، robots، RTL/`fa-IR`، JSON-LD Article+Mountain |
| دسته‌بندی | نرمال‌شده روی taxonomy معتبر |
| هاب | فقط زمانی (جدیدترین اول) — قانون محصول |
| گزارش مرتبط | لیست تخت «گزارش‌های مرتبط :» |
| هوا | فقط منابع دقیق قله؛ رفرش ۴× روز تا شب قبل (اتوماسیون تا شارژ Cursor متوقف) |
| صفحهٔ اصلی | هویت فردی (مهندس + کوهنورد)، نه هاب گزارش |
| Search Console / Bing | باید توسط مالک ثبت شود |
| اعتماد دامنه | `pop.kavehrs.com` محتوای اسپم — آسیب به Trust |
| شکاف رشته | `glacier` = ۰، `wall-climbing` = ۰ |
| مختصات قله | فقط بخشی از گزارش‌ها `latitude`/`longitude` دارند |

### پوشش فعلی (تقریبی)

- کوهپیمایی / قلل البرز نزدیک تهران: قوی‌ترین لایه
- کوهنوردی فنی (تیغه دارآباد، ژاندارم خلنو، ناز–میشینه‌نو): تمایز خوب
- ارتفاع بالا: کهار، خله‌نو، لشگرک، ناز
- یخ‌نوردی: دو گزارش خور (آبشار ۵ و کرجی‌ها)
- سنگ‌نوردی: شقایق + پل‌خواب
- صعود زمستانه / برفچال: چند مورد
- یخچال و دیواره‌نوردی واقعی: خالی

### رقبا در SERP فارسی

- باشگاه اسپیلت، باشگاه تهران، توچال، آلپ: حجم بالا، گزارش کوتاه باشگاهی، گالری
- ویکی‌کوه / فروم‌ها: مشخصات قله، نه روایت اجرایی با هوا و تجهیزات تاریخ‌محور

**شکاف بازار که این سایت می‌تواند پر کند:** گزارش عملیاتی پیش از صعود + تکمیل پس از اجرا، با هوا از منبع دقیق همان قله، تجهیزات وابسته به همان پیش‌بینی، و روایت یکتا — چیزی که باشگاه‌ها معمولاً نمی‌نویسند.

## اصل غیرقابل‌مذاکره (از گوگل + قوانین سایت)

- محتوا برای خواننده ساخته شود، نه برای موتور جستجو.
- گزارش ساختگی، بازنویسی ادبیات قله، یا دو متن تکراری برای یک قله: ممنوع.
- طول متن هدف گوگل نیست؛ کامل بودن عملیاتی هست.
- اتوماسیون/AI فقط برای قالب، هوا، و بهداشت فنی — نه تولید انبوه گزارش برای رتبه.
- هاب `/logbook/` زمانی می‌ماند؛ دسته‌بندی فقط برای انتخاب گزارش مرتبط در پشت صحنه.

## فاز ۰ — اعتماد دامنه (مالک؛ بدون این، بقیه ضعیف است)

بدون Trust، E-E-A-T از نظر گوگل کامل نمی‌شود. Trust مهم‌ترین جزء است.

1. حذف DNS ساب‌دامین‌های اسپم (`pop.kavehrs.com` و مشابه) — `_seo/subdomain-dns-checklist.md`
2. ثبت مالکیت در [Google Search Console](https://search.google.com/search-console) برای `https://www.kavehrs.com` **و** دامنهٔ `kavehrs.com`
3. ارسال sitemap: `https://www.kavehrs.com/sitemap.xml`
4. همین کار در Bing Webmaster Tools
5. بررسی Security issues / Manual actions بعد از پاکسازی DNS
6. شارژ حساب Cursor و روشن کردن اتوماسیون هوا + SEO روزانه

خروجی قابل‌اندازه‌گیری: GSC نشان دهد URLهای `/logbook/` ایندکس شده‌اند و خطای پوشش ایندکس برای گزارش‌ها نزدیک صفر است.

## فاز ۱ — هویت مرجع روی خود سایت

الان صفحهٔ اول «دربارهٔ مهندس نرم‌افزار» است. برای مرجع گزارش صعود باید **بدون تبدیل سایت به مجلهٔ کلی** مشخص شود که logbook محصول اصلی کوهنوردی است.

کارهای پیشنهادی (وقتی مالک تأیید کرد):

1. در صفحهٔ اصلی: یک بلوک کوتاه با لینک برجسته به `/logbook/` و ۲–۳ گزارش شاخص (کهار ۱۴۰۵، خلنو ژاندارم، یخ‌نوردی خور) — نه بازنویسی کل هویت.
2. صفحهٔ درباره: سابقهٔ کوهنوردی، رشته‌ها (DryTooling، ارتفاع، فنی)، و لینک به آرشیو گزارش — «Who» در راهنمای گوگل.
3. بایلاین ثابت روی گزارش‌ها (نام + لینک به درباره) اگر در قالب هنوز ضعیف است.
4. تکمیل `peak.latitude` / `peak.longitude` فقط وقتی مختصات معتبر است — JSON-LD Mountain کامل‌تر می‌شود.
5. عکس واقعی هر برنامه در پوشهٔ slug؛ OG از لوگو نباشد.

## فاز ۲ — موتور محتوا: هر برنامهٔ واقعی = یک گزارش مرجع

ریتم: **هر صعود واقعی یک گزارش کامل**، از لحظهٔ تصمیم تا تکمیل پس از برنامه.

قالب برتری نسبت به باشگاه‌ها (از قبل در قوانین هست — باید روی هر گزارش جدید سخت‌گیرانه اجرا شود):

| بخش | چرا مرجع می‌سازد |
|---|---|
| مشخصات قله + مختصات | پاسخ مستقیم «قله X کجاست / چند متر» |
| هوا از منبع دقیق همان قله | تصمیم بسته‌بندی و go/no-go |
| چالش‌ها با قبل→بعد | شفافیت؛ نه عدد خام بدون تفسیر |
| تجهیزات وابسته به همان تاریخ | تمایز کامل با لیست فصلی باشگاه |
| زمان‌بندی اجرا پس از صعود | تجربهٔ دست‌اول (E در E-E-A-T) |
| عکس مسیر/تیم در پوشهٔ URL | اثبات حضور در محل |
| گزارش مرتبط هم‌رشته | خوشهٔ موضوعی بدون صفحهٔ نازک |

اولویت پوشش (فقط اگر برنامه واقعاً اجرا شود):

1. **تکرار قلل با روایت جدید** (مثل کهار ۱۴۰۲ vs ۱۴۰۵) — گوگل duplicate را جریمه می‌کند؛ روایت باید یکتا بماند.
2. **پر کردن رشته‌های خالی با صعود واقعی:** دیواره‌نوردی، یخچال، DryTooling اگر اجرا شد.
3. **قلل جستجوشوندهٔ البرز که هنوز گزارش ندارید** (فقط پس از صعود): دماوند، آزادکوه، علم‌کوه، شاه‌البرز، توچال زمستانه، …
4. **یخ‌نوردی / DryTooling:** رقابت فارسی ضعیف‌تر است؛ دو گزارش خور هستهٔ خوبی است — با برنامه‌های بعدی گسترش دهید.

صفحات «راهنمای قله» جدا از گزارش صعود نسازید مگر ارزش یکتا داشته باشند (نقشه، جدول مسیرها، لینک به چند گزارش واقعی). صفحهٔ نازک keyword برای «مسیر صعود X» خلاف people-first است.

## فاز ۳ — معماری کشف (بدون شکستن قانون هاب)

هاب `/logbook/` زمانی می‌ماند. کشف بهتر از راه‌های دیگر:

1. عنوان و description هر گزارش: قله + نوع برنامه + منطقه + سال جلالی — بدون keyword stuffing.
2. لینک داخلی از گزارش‌های هم‌قله به یکدیگر (کهار ۱۴۰۲ ↔ ۱۴۰۵ از قبل در related می‌آید اگر دسته مشترک باشد).
3. در صورت نیاز بعدی: صفحهٔ `/logbook/peaks/` فقط فهرست قلل با لینک به گزارش‌ها — بدون کپی متن گزارش. این صفحه را فقط وقتی حداقل ~۸–۱۰ قله با چند گزارش دارید بسازید.
4. فیلتر رشته روی هاب نگذارید (قانون محصول). اگر روزی لازم شد، صفحات جدا با `noindex` یا خارج از هدف رتبه نسازید مگر مالک صریحاً بخواهد.

## فاز ۴ — اعتبار بیرونی (Authoritativeness)

گوگل مرجع بودن را از **ذکر دیگران** هم می‌فهمد. کارهای مشروع:

1. بعد از هر برنامه: لینک گزارش را در باشگاه میزبان، گروه همنورد، و اینستاگرام با URL کامل بگذارید (نه فقط اسکرین‌شات).
2. اگر باشگاه گزارش شما را بازنشر کرد، بخواهید به URL اصلی لینک بدهند.
3. مشارکت در بحث‌های فنی (مسیر، هوا، ایمنی) با لینک به گزارش مربوط — نه تبادل لینک.
4. پروفایل‌های `sameAs` (لینکدین، گیت‌هاب، اینستاگرام کوهنوردی) یکدست بمانند.
5. از خرید بک‌لینک، شبکهٔ PBN، و دایرکتوری اسپم پرهیز کنید (سیاست اسپم گوگل).

## فاز ۵ — تجربهٔ صفحه و نگهداری

- عکس‌ها: حجم معقول، alt فارسی معنادار، cover واقعی.
- Core Web Vitals: قالب سادهٔ فعلی کمک است؛ تصویر غول‌پیکر اضافه نکنید.
- گزارش‌های قدیمی: فقط اصلاح واقعیت/مسیر تصویر/metadata — بازنویسی SEO برای «تازگی جعلی» نکنید (گوگل صریحاً نهی کرده).
- ایجنت روزانه SEO: فقط blocker و hygiene؛ نه بازنویسی روایی.

## اندازه‌گیری موفقیت

در GSC (بعد از فاز ۰) این‌ها را دنبال کنید — نه «رتبهٔ کلی سایت»:

| سیگنال | معنی مرجع شدن |
|---|---|
| Impression برای `گزارش صعود {قله}` | کشف موضوعی |
| کلیک روی URLهای `/logbook/` | انتخاب در SERP |
| رتبه برای قلل پوشش‌داده‌شده (کهار، خله‌نو، خور یخ) | عمق خوشه |
| ایندکس کامل ۲۲+ گزارش | بهداشت فنی |
| ارجاع از باشگاه/اینستا به URL | اعتبار بیرونی |

هدف کیفی: برای قلل و رشته‌هایی که **گزارش دست‌اول دارید**، صفحهٔ شما گزینهٔ اول خوانندهٔ جدی باشد — نه اینکه برای همهٔ قلل ایران صفحه داشته باشید.

- رها کردن ساب‌دامین اسپم
